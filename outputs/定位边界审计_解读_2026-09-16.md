## 六、门禁怎么用

```bash
npm run check:boundary                          # 单独跑审计
npm run ci                                      # 已接入为 [边界] 步骤（第一步，不依赖工具链，约 1 秒）
BOUNDARY_UPDATE_BASELINE=1 npm run check:boundary   # 清理后收紧基线
BOUNDARY_SKIP=1 npm run ci                      # 应急跳过
```

**门禁规则**：

- **棘轮（ratchet）**：基线在 `scripts/boundary-baseline.json`（当前：死命令 14，死配置 0），**只许降不许升**。新增长进来的引擎能力一旦零引用，立即撞门禁。
- **硬失败（不受基线影响）**：
  - 幽灵调用 —— 前端 invoke 了但 Rust 未注册 → 运行时必挂
  - 未挂载命令 —— 标了 `#[tauri::command]` 却没进 `generate_handler!`
- **报告**：每次运行刷新 `outputs/定位边界审计.md` 与 `outputs/boundary-audit.json`。

## 七、这次审计本身的教训

第一版脚本报了 **27 个死命令**，是错的——它只认 `invoke(`，漏了 `invokeJson(` 这个封装，把 13 个真正在用的命令误判为死命令。修正后是 14 个。

这正好复现了 8-29 复盘记录的方法论教训：**搜调用关系要搜符号与字面量，不要搜路径模式或单一函数名。** 现在脚本采用「剥离注释后搜字符串字面量」的策略，对任何封装形式都成立——但**新增封装层时仍需注意**，脚本已把无法静态校验的调用单独列出（`动态 invoke`）。

## 九、门禁盲区已补：TS 层孤岛（同日追加）

### 起因

第七节写完才发现：上面那套门禁**只守了前门**。它审的是「Rust bridge ↔ 前端 invoke」这一条边界，**TS 引擎层完全不在视野内**。

补上可达性分析后，**首跑即抓到 12 个从入口不可达的模块**。

### 判定方式

从 `index.html` 的 `<script src="/src/main.tsx">` 出发，沿相对 `import` / `export-from` / 动态 `import()` / `require()` 建图，再与从 `*.test.*` 出发的可达集比对：

| 档位 | 含义 |
| --- | --- |
| **完全无引用** | 入口不可达、测试也不可达 |
| **仅自测可达** | 只能从测试到达——即「有实现 + 有自测 + 零产品调用」 |

两档都算孤岛。**「只在测试里跑通」和「完全没接线」在边界意义上是同一件事。**

### 12 个孤岛（分组）

| 分组 | 模块 | 性质 |
| --- | --- | --- |
| **战略模块未接线** | `bidirectionalCompiler/index.ts`、`bidirectionalCompiler/types.ts`、`bidirectionalCompiler/worldPackage.ts`、`storyVeinDetector.ts`、`branchExplorer.ts`、`LnnReportCard.tsx` | 共 1223 行，只互相引用，**不进 `dist`**。正是战略文档里的「故事矿脉探测器」（模块 1）、「分支探索器」（模块 4）、「世界—小说双向编译器」 |
| **重复实现（一套已死）** | `utils/frontendLogger.ts` | 与已接线的 `utils/logger.ts` 功能重叠：`main.tsx:18,23` 装的是 `logger.logError`，`frontendLogger` 无人 import |
| **翻译未接线** | `engines/wanxiang/translation.ts`、`utils/translationStore.ts` | 与 08-29 出海调研「翻译是空壳」的结论一致；`translation.ts` 仅被 type-only 引用 |
| **有实现有自测零调用** | `engines/wanxiang/settingConsistency.ts`（386 行） | 与 Rust 那批死命令形态完全一致 |
| **遗留 barrel / 门面** | `types/index.ts`、`engines/wanxiang/ai-entry.ts` | 前者是无人 import 的汇总出口（大家都直接 import `types/novel` 子路径）；后者是「AI 可直接 import」的门面，零引用 |

### 一个方法学验证

`src/types/index.ts` 这个孤岛值得单独说：用 grep 搜「谁 import 了 types」会得到 23 条命中，看起来完全正常。但那 23 条全是 `from './types'`——**相对于 `src/engines/wanxiang/` 的 `types.ts`，不是 `src/types/index.ts`**。

门禁按「相对于引用文件解析」来处理，所以判对了，grep 判错了。**这正好说明为什么边界检查必须写成分辨路径的脚本，不能靠 grep 拍脑袋。**
